# 10 · 部署、运维与故障恢复

## 1. 部署单元与环境

API、dispatcher/定时协调器、Worker分进程部署，Worker按识别/图片/视频后期负载设并发。PostgreSQL与私有对象存储是持久依赖；日志/指标不能充当任务数据库。API横向扩容不改变任务唯一性，Worker重启依持久阶段恢复。

本地Windows原生运行；后续云端可用受控主机/托管服务，采用进程服务管理，初版没有容器依赖。不调用本地Docker、WSL、虚拟机、Testcontainers或隐式拉起它们的脚本。云账户/地域/规格/预算未选，本文是部署合同，不是已开通环境。

development/test/staging/production使用独立库、桶/对象前缀、密钥、商户和回调域名。测试默认拒绝生产地址，生产禁止mock模型、演示支付和本地文件存储。配置不完整或能力未准入时拒绝销售，不能自动降级为假成功。

## 2. 发布顺序与回滚

发布前保存提交/构建、lockfile、SBOM、配置非秘密摘要、原生工具版本、schema迁移与兼容矩阵。先备份并确认恢复可用→expand迁移→部署能兼容旧新数据的API/Worker→小流量验证→切换→回填校验→后续版本清理旧字段。

Worker停机先停止领取新stage，持有任务在有界时间内完成或保存可恢复状态，不能直接释放UNKNOWN付费预算。API/dispatcher重启不得重复建任务。大规模退版本前先核旧代码是否读得懂当前快照/状态；不兼容时停止新售、保持在途兼容处理并向前修复，不能执行破坏性down冒充回滚。

销售开关粒度为全局、渠道、preset/variant、模型/资源；停新售与已付履约开关分离。停新售不能把已付订单无声丢进永久队列。生产启售需实际准入、价格、渠道与G4证据，示例.env开关不授权上线。

## 3. 监测与健康

API存活检查只反映进程；就绪检查依数据库/必要配置/迁移状态。Worker健康报告心跳、可领取阶段、最老排队年龄和租约；对象/模型不可用触发依赖降级/停售，而不是无限网络重试。

指标至少包括：请求延迟/错误、会话失败、上传确认失败、识别阻断、队列年龄、三路线p50/p95与硬截止、供应商UNKNOWN数/年龄、预算预留/实际成本、修复率、QC拒绝、整包成功率、验付未履约、退款待确认、相册失败回执、清理积压。每单以trace_id/order_id关联，指标标签不用个人信息或无限高基数字段。

初始告警规则是设计建议：任何已付未建履约任务、预算越限、重复扣费/退款、私有越权、终止单公开均立即告警；UNKNOWN和最老队列根据合同剩余时长告警；p95/成功率按路线窗口统计。阈值/通知接收人/值守安排在发布前确认，不默认向外发消息。

## 4. 故障处置手册

| 现象 | 先做什么 | 恢复与禁止 |
| --- | --- | --- |
| 已付但无任务 | 查原渠道/订单、payment_events、outbox和事务 | 幂等补投原事件；不让用户再付一次 |
| 供应商提交超时 | 锁原意图，保留成本预留，查任务/对账 | 确认结果再推进；不直接新POST重购 |
| Worker崩溃/租约过期 | 检查stage代次、提交记录、已下载hash | 新Worker接管并查询原供应商；旧代次不可写 |
| 媒体/QC失败 | 隔离产物，确认剩余预算/截止/一轮修复额度 | 合同内修复或原单失败退款；不局部发布 |
| 模型/资源撤下 | 精确停售受影响版本，列出已售快照 | 按原合同履约/异常退款，不自动换声音/路线 |
| 私有URL/密钥泄露 | 停签/撤销轮换，限制访问，保留脱敏审计 | 评估既有短链/外部副本，不声称全部即时撤回 |
| 数据恢复/删除遗漏 | 隔离服务、核恢复点，重放删除/支付后续事件 | 对账后逐步开放；不直接恢复旧权益/已删媒体 |

每次事件记录影响订单/版本、时间线、资金/媒体范围、处置者、恢复证据与后续改进。人工补偿不修改原始支付/供应商账簿；用追加分录和关联记录。

## 5. 备份、清理与容量

数据库做可恢复备份/WAL或托管等效能力；私有对象按实际生命周期和恢复能力配置。发布前明确RPO/RTO及成本并做原生恢复演练；当前没有已达成的灾备指标。演练覆盖快照后验付、UNKNOWN、未投outbox与删除标记，不能只检查备份文件存在。

清理器先按合同终止授权，再分批删除对象/版本/缓存和过期私有数据，写幂等回执与失败重试。活动任务需引用固定保留对象；未引用临时文件有独立到期，不让磁盘满后影响所有订单。

容量预算计入三路线并发、每任务CPU/内存/临时磁盘、存储/下行、供应商限流与队列等待。并发上限以实际压测和截止约束设定，过载在报价/新售入口限流；已付任务优先按合同执行，不能因新预览抢满资源。

## v1.1 Codex修订

原生Codex app-server以stdio受管运行，固定构建与协议哈希，不外露端口。先持久检查点/意图再重建；终态写释放outbox，60秒扫描孤儿、30秒停止宽限、5分钟回收目标、10分钟告警均待G0。UNKNOWN由独立对账器继续处理，不重购/重复交付。

2026-10-28已增加独立回收服务入口 `dev:reaper` / `start:reaper`，部署时与API、制作Worker分别监督；框架不依赖原Worker的finally。实际Node子进程/持久队列故障测试不证明受限OS身份与完整进程树清理，原生launcher准入及目标SLO仍待验证。详见[回收与保留实施](../实施/独立实例回收与冻结输入保留-v1.0.md)。

媒体持久对象另由`dev:media-maintenance` / `start:media-maintenance`独立维护，每60秒扫描，按对象租约/代次执行精确删除并保留失败回执。关闭付费制作开关仍可运行；生产OSS维护请求本身有运维费用。部署需分别监督API、制作Worker、实例Reaper和媒体维护器。维护器先核对UNKNOWN原字节、视觉/Codex原回执，结清后执行受控32表在线字段脱敏；不强制清除未决原数据。底层数据库页/WAL、供应商副本和备份恢复门禁仍待补齐，详见[媒体回收实施](../实施/私有对象登记与媒体物理回收-v1.0.md)。

详见[Codex服务专项](14-Codex内核与分阶段编排.md)及[实施验证](18-Codex接入验证与实施计划.md)。
