# 独立实例回收与冻结输入保留

2026-10-28｜需求 v3.1 / 开发契约 v1.1｜应用仍为 IN_PROGRESS。

本次实现独立于原制作 Worker 的持久回收队列、统一释放授权、回收代次与不可变清理尝试记录；修正未付订单提前延期及整个商品照片一起延期的问题。完整三路线、真实 Codex、生产原生隔离与实际进程树清理、设备和部署仍待验收。以下故障测试使用显式合成清理端口，不能据此开放销售。

## 入口与职责

| 范围 | 实现 |
| --- | --- |
| 持久字段和不可变记录 | `src/api/db/migrations/013_instance_cleanup_queue.sql` |
| 统一释放授权 | `src/worker/lifecycle/instance-release.ts` |
| 独立领取、扫描和回执 | `src/worker/lifecycle/reaper.ts` |
| 原生清理协议适配 | `src/worker/codex/launcher.ts` 的 `NativeDetachedCleaner` |
| 受控目录清理 | `src/worker/lifecycle/cleanup-files.ts` |
| 独立服务入口 | `src/worker/lifecycle/reaper-main.ts` |
| 冻结照片保留 | `src/api/modules/retention.ts` |

业务 API、制作 Worker、独立回收器使用分别运行的原生进程，数据库保存工作状态。启动方法：

```powershell
./scripts/run.ps1 dev:api
# 另一个本项目终端
./scripts/run.ps1 dev:worker
# 再一个本项目终端，独立于制作 Worker
./scripts/run.ps1 dev:reaper
```

`build:server` 同时构建三者及 MCP 桥接；编译后回收器入口为 `start:reaper`。`./scripts/run.ps1 exec tsx src/worker/lifecycle/reaper-main.ts --once` 可检查一次扫描/领取，不能代替长期服务。回收器不要求启用收费、模型或销售开关，不重新购买推理，也不要求续签已过期的模型准入。真实 launcher 构建仍须存在且与原冻结摘要一致。

## 从登记到释放

1. 角色分配时持久化 `YPCC-CLEANUP-1` 协议标记及实例/运行关系。
2. 在原生启动前，事务保存不可变 `cleanup_binding`：无凭证的启动清理计划、nonce、运行与目录、launcher 路径和 SHA-256。数据库中的清理计划 `environment` 必须为空；原启动计划中的临时凭证仅在实例控制域使用，清理时一并删除。
3. 启动前保存绑定、启动后激活实例都检查实例代次；已被回收器领取的实例不能重新激活。
4. 正常结束、暂停、失败、取消或交付写 `ReleaseRequested`。统一授权入口先锁订单再锁实例，拒绝仍有有效执行租约且未形成停止状态的角色；管理操作携带预期代次并沿用审计。旧事件不能直接终止正常运行中的角色。
5. 独立回收器每 60 秒扫描一次失去有效阶段/订单或实例租约的孤儿。事件仅申请释放，真正清理由独立持久队列领取。
6. `FOR UPDATE SKIP LOCKED` 领取清理任务，增加实例 fencing 和 `cleanup_generation`，设置 60 秒清理租约并撤销全部能力。每个目录操作和最终回写检查所有者、代次和租约；旧所有者不生成覆盖新状态的回执。
7. 使用原冻结的 launcher 执行 `release --manifest`，核验 nonce、运行、登记进程引用、退出/凭证/临时文件证明，再检查实际目录。清理 helper 限时 30 秒。
8. 确认没有 RUNNING/QUEUED 后台工具、实际临时目录及控制目录均消失、能力已撤销，才记录 RELEASED。否则记录 CLEANUP_FAILED，持久重试间隔默认 60 秒。十分钟未清理输出脱敏 `cleanup_overdue` 事件，告警投递和值守接入仍待部署。

每次清理尝试独立追加一份不可变 `cleanup_receipt`。它记录新代次、退出与目录检查、撤权、证据摘要、错误码及未决供应商任务；未决推理引用保存在私有字段。失败尝试不被重试覆盖。

供应商 UNKNOWN、推理 UNKNOWN 和成本预留继续由原持久记录负责，清理不会取消或释放不明确费用，也不重发付费动作。已交付成品和审计记录位于持久域，实例目录删除不删除交付物。

尚未启动且有新协议登记、无进程与隔离证据的实例允许直接清理其受控准备目录。旧实例缺少绑定时保留 CLEANUP_FAILED，等待核对；不能按 PID 名称、猜测路径或其他订单数据强行清理。路径清理验证项目根、精确运行根及逐层文件，拒绝 junction/符号链接和越界路径，不执行递归 shell 删除。

## 原生 launcher 的未完成边界

生产路径仍依赖尚未提供/准入的原生 `.exe`。它必须持久保存 nonce 与受限身份/Job Object 进程组登记，并在清理后拒绝同 nonce 的迟到启动；释放须幂等，能够在原 Worker 崩溃、启动回执尚未回传、角色退出或模型准入过期时重放。

本次测试清理端口只能在 `APP_ENV=test` 注入。测试直接登记实际 Node 子进程并持有其句柄，验证退出和实际目录；这证明持久回收状态机与独立运行，不证明真实 Codex、低权限 OS 身份、网络隔离、完整进程树或未登记的媒体子进程清理。RUNNING/QUEUED 工具阻止完整释放，生产工具的进程组归属与最终停止仍须补齐。不得以 JSON 的 `true` 或 synthetic 身份冒充这些生产证据。

## 输入保留规则

| 事件 | 实际行为 |
| --- | --- |
| 上传、创建商品 | 沿用未付 24 小时保留；不因选方案或创建订单延期 |
| 创建未付款订单 | 只创建订单/原支付意图，不更新照片或商品到期时间 |
| 有效付款确认 | 保留资金事实；只对原订单固定的照片版本、照片集摘要及 3–5 张实际 READY/未过期照片延期七天 |
| 交付发布 | 同一事务将冻结照片的权益延长至交付清单到期时间，保证领取/允许修改周期；其他有效订单已有更长期限时取较晚值 |
| 重复支付通知 | 重放原已确认结果，不刷新照片保留期 |
| 已删除、撤权、缺图、过期或摘要不符后付款 | 保留实际付款与账簿，取消履约并请求原路退款，不建制作任务、不复活输入 |

冻结定位使用 tenant、owner、product、photo revision 和 photo-set hash，按固定顺序重新计算实际资产摘要；不会跟随商品当前照片版本，更不会将同商品其他版本或未绑定照片一起延期。报价/下单也拒绝已过期商品。

后续媒体回收专项已将锁顺序统一为用户媒体事务锁→订单→商品→资产→对象，协调删除、写入与付款。原专项只完善访问撤销和支付兼容；新增的受控对象登记和本地物理删除见[媒体回收实施](私有对象登记与媒体物理回收-v1.0.md)，供应商/复制副本、数据库内容脱敏、未决原回执对账和备份标记重放仍待完成。数据库到期字段不单独构成物理删除证明。
