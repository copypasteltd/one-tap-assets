# 最终交付入口与构建收口 v1.0

本轮按用户要求优先完成可交付主功能，不以全面测试或全面绿灯作为打包前提。需求v3.1、C设计、现有商品/订单/费用/复核协议及禁用真实服务的默认值继续有效。

## 1. 已有主功能与本轮范围

小程序拍照上传、多模态商品档案、社区及10套官方预设、冻结清单/报价、原渠道主动付款、分阶段制作/后期/QC/事实和风格独立复核、交付领取和相册队列已有源码。Plus已有图片调整、2至10件图片独立批量，以及视频选段/裁切/定时字幕/保留原声或静音、新MP4与封面/文案交付。上一轮选段容量修正及原生专项证据按原来源保留。

本轮集中修正启动与交付产物不一致：`delivery:build`输出独立目录，而旧`local:start`/`doctor`默认检查固定`runtime/build`。仓库中可能存在旧产物，因此“文件存在”不能代表当前交付正在运行。

## 2. 当前构建选择

`scripts/delivery/resolve-build.ts`读取`docs/delivery/current.json`，验证记录内的源码、运行契约、字体和所选产物SHA256。仓库优先使用当前记录的独立目录；独立目录不存在时，按同一记录验证ZIP映射后的`runtime/build`。当前目录存在但字节不符时直接失败，不静默回退。

后端选择还验证本轮成功的Plus页面，向所有所属子服务显式传递同一`YPCC_BUILD_ROOT`，避免API静态页面另指向旧目录。回放和`doctor`使用同一选择逻辑。所有路径留在项目内，拒绝链接/junction。环境显式指定构建目录时，属于开发者主动选择，记录为`EXPLICIT_LOCAL`和`hashes_verified=false`；无交付记录的原始本地构建记录为`LOCAL_DEFAULT`。

该校验处理构建一致性，不提供进程或客户数据隔离，也不是生产准入。`setup-local.ps1`改为通过`delivery:build --skip-mini`生成与本地源码一致的新记录。

## 3. 快速交付命令

```powershell
.\scripts\run.ps1 delivery:final
.\scripts\run.ps1 delivery:final --skip-mini
.\scripts\run.ps1 delivery:final --server-only
```

默认执行类型检查和服务端/Plus/支付宝/抖音构建，然后打包，不运行全面测试。不允许同时指定两个缩减选项，也不接受测试扩展选项。类型/服务端/Plus各180秒，两个原生编译器各360秒；原生工具初始化的既有超时诊断仍保留。

构建必须生成新记录后才能进入打包，不能在启动构建失败后借用旧记录。已记录的部分目标失败仍可生成如实标注缺项的源码包，命令保留非零退出码。中断会停止所属命令树，停止后续打包。摘要存于忽略目录`runtime/delivery/final.json`；交付状态以`docs/delivery/current.json`和`package.json`为准。

ZIP内生成独立的`docs/delivery/package.json`描述，使解压后清单链接可用。它指向根目录`DELIVERY-MANIFEST.json`，不写入自身ZIP摘要；完整ZIP的SHA256由包外`SHA256SUMS`及仓库交付指针提供，避免自引用。最后仅此打包器源码变化，类型重新核对，179份已通过的编译产物逐份SHA保留；编译/十项检查/原生启动的原执行源另行封存，不重复运行未变化业务。

ZIP补入根目录`START-HERE.md`、`.editorconfig`和`.github`中的公开协作文件。保留全部源码、文档、冻结设计和已有截图/录屏/GIF，仅纳入当前成功产物；不带密钥、数据库、客户素材、工具及依赖目录。

## 4. 关键检查与边界

本轮只选构建选择的6项和原就绪逻辑的4项检查，覆盖新旧产物同时存在、解压后映射、实际页面字节被修改、源码变化、失败组件、显式本地目录和junction拒绝。随后使用当前原生服务进行启动/就绪/停止检查，核对Plus页面实际字节；原生探针首次误以API根目录解析相对资源而失败，纠正探针后实际Plus资源核对通过，未修改产品代码；该诊断也保留。具体结果和未执行项见[本轮证据](../verification/final-closure-source.json)。完整测试不执行。

无业务API、数据库迁移、客户端页面、生成/预算/支付/清理协议或冻结样式变更；因此不重复运行原生媒体制作全链路或重新录制界面。历史媒体与验证文件保留原字节；三份滚动验证索引更新前另存本轮基线版本。

## 5. 生产隔离边界

当前仓库提供`NativeRoleLauncher`的受控调用与清理协议，尚未随仓库提供准入合格的隔离器`.exe`。按[现有实例协议](../开发/16-实例隔离与释放协议.md)，仍需专用OS身份、ACL、进程树/资源/网络限制和实际清理证据。仅开启Codex自身命令沙箱，不能替代整个app-server角色的宿主隔离。

本轮只阅读官方资料，不创建系统账号、不改全局系统策略、不启用MXC、不调用Docker/WSL/虚拟化。OpenAI将`elevated`作为需要管理员预配置的Windows原生方案；其命令权限边界不能直接证明平台角色整体隔离。依据：[Windows sandbox](https://learn.chatgpt.com/docs/windows/windows-sandbox)、[Codex App Server](https://learn.chatgpt.com/docs/app-server)。平台仍坚持独立的受限启动器准入，真实收费/生成开关保持关闭。
