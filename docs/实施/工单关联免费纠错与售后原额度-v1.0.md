# 工单关联免费纠错与售后原额度

2026-10-30。对应F12、F14、F41；保留58项需求/52项P0、三制作路线、官方10风格/至少14变体及C「柚子创作社」设计。完整产品、生产准入与云端部署仍为false。

本次将原先仅登记不完整PLATFORM_REPAIR记录的管理入口，接入既有五阶段售后执行链。当前实际范围是冻结了售后能力的已付款、已交付、未撤权且仍在有效期内的原图无声订单。执行对象仍为原商品、原清单和原合同。

| 编号 | 可处理内容 | 交付变化 |
| --- | --- | --- |
| 01 | COVER：更正素材包封面 | 选择本包另一张现有图片，保留原媒体字节 |
| 02 | ALLOWED_ORDER：更正素材列表顺序 | 全部原素材完整、不重复地重排展示顺序 |
| 03 | DISPLAY_TEXT：更正配套文案 | 受原商品事实约束，写入新的实际UTF-8文件，再验收 |

这些操作不表示重绘商品画面、修改视频内字幕、重录口播或重新生成视频。生成式及有声售后仍待实现。当前客服网页提供工单沟通；纠错执行由有独立`support:repair`权限的运营调用管理接口，尚未新增网页纠错编辑面板。

## 1. 使用顺序

1. 用户在原订单反馈素材问题，服务端保留私有说明及可选证明图片。
2. 有权限的客服接单，工单处于PROCESSING；PRODUCT_ERROR、GENERATION或OTHER可用于本次素材纠错。
3. 原接手客服核对原问题、当前完整素材清单及清单版本，提交一种具体修改。工单版本及当前清单版本必须准确。
4. 原事务绑定工单/客服/问题摘要、原父清单、原合同和执行快照；创建五阶段REVISION并返回原revision_id。工单版本递增，一张工单只关联一个纠错请求。
5. 新POST角色调用受控工具；新QC读取全部真实文件；新事实、风格角色分别复核完整包；平台最终事务重查并发布新版本。
6. 用户从原订单修改记录查询REQUESTED/PROCESSING/COMPLETED/FAILED。成功后领取最新完整包；原包不可变，新包沿用原成品到期时间。

客服的“回复/解决/关闭”和制作执行状态分别记录。提交纠错不会自动解决工单；只有实际新版本发布才能视为纠错制作完成。发布失败时原交付保持可领取；本入口不发起退款，也不重开原制作实例。

连续修改会逐一核对已完成的父版本：不可变清单、原冻结输入、候选包、原制作证明及两份独立报告，直至回到原始封存媒体。前次已验收的新文案可成为下一次的合法父素材；新请求仍必须形成自己的检查点和复核报告。PostgreSQL的时区日期文本与清单的ISO日期可以表示同一时刻，比较时只接受同一有限时间戳，原存储摘要、原截止及领取期不变。

## 2. 接口与请求

沿用77业务/30管理操作。新增`PlatformErrorRepairRequest`，替换管理入口原来的泛用动作请求；返回已有Revision结构。原来的任意evidence_record_ids请求会被契约拒绝，不能继续提交缺失冻结输入的任务。

```http
POST /v1/internal/p01/orders/{order_id}/platform-repairs
Authorization: Bearer <独立客服令牌>
Idempotency-Key: platform-repair:<本次原意图编号>
Content-Type: application/json
```

```json
{
  "ticket_id": "ticket_example",
  "expected_ticket_revision": 1,
  "change": {
    "kind": "DISPLAY_TEXT",
    "manifest_revision": 1,
    "display_text": "经原商品资料核对后的配套文案"
  }
}
```

令牌、工单和ID均为占位示例；文案必须通过本单事实校验，不能把示例直接用于任意商品。COVER改用`cover_deliverable_id`，ALLOWED_ORDER改用完整`ordered_deliverable_ids`，一次不能混合多种字段。

请求得到Revision，其中`consumes_user_allowance=false`；成功后仍为false，`result_manifest_revision`指向新版本。接口受理不等于交付完成。丢失回执后用同一键及完全相同正文重试，取回原请求；不同正文同键409。不同键不能为已关联的同一工单重复执行。页面重载后需恢复原操作记录，不能自行生成新工单规避失败。

## 3. 原合同、额度和截止

沿用报价前冻结的`YPCC-LIMITED-REVISION-1`。免费纠错不消耗用户的一次成功小修改次数；费用、调用次数和Token并不因此免费或无限。

- 所有用户修改与平台纠错共用原订单唯一的revision_budgets，花费/预留/UNKNOWN累计。没有该合同的历史订单不得补写能力或加价上限。
- 整个售后账户累计推理次数、各角色次数、输入/输出Token和推理费用；所有revision_id的工具调用同样累计，不能换编号重置。
- 创建新请求不会新增售后额度；首次制作保留的售后金额仍在原订单总额内。额度不足时执行拒绝，不能承诺一定能完成第二次修改。
- 有在途或UNKNOWN费用时阻止新请求，等待原回执恢复。失败可释放成功次数，实际花费/次数不归零。
- 任一时刻同单最多一个REQUESTED/PROCESSING请求，避免两个候选同时替换同一父版本。
- 截止为“本次受理后300秒、首次交付后48小时、原成品到期时间”的最早值；所有五阶段保存相同绝对截止，恢复不续期。原订单的制作截止始终不改。

## 4. 权限、证据和隐私

管理域仍使用独立身份与`support:repair`权限，普通买家会话不能提升。只有原接手客服可提交；跨订单工单404，非接手人403，旧工单版本409。原工单已解决/关闭、未接单、已关联纠错或错误用途均拒绝。

原私有说明、附件ID及问题类型形成证据摘要，与原客服/工单版本一起冻结。后续每次阶段与工具读取都会重验同一原工单、归属、原关联和摘要，主动删除、退款、许可撤销或媒体到期仍即时阻断。不能仅凭工单ID或管理审批绕过许可、事实或实际文件核验。

私有说明/修改文案位于既有私有载荷与REVISION隐私范围；管理幂等只保存不含正文的Revision元数据，审计保存请求摘要。原封存包及独立复核仍需新报告，不能复用先前PASS。交付后请求独立实例释放；生产受限身份/供应商/备份删除等仍须真实准入。
