# 逐张拍照与原上传批次 v1.0

2026-10-30。对应 P01-F02、F03、F06、F15、F23、F43，需求 v3.1 和全部 58 项范围不变。双小程序沿用共享页面及 C「柚子创作社」颜色、字体层级和按钮样式；冻结设计原件保持原字节。

## 1. 解决的问题

旧拍照入口一次调用相机/相册选择，并要求这一次返回 3–5 张照片。手机相机一次返回一张时，用户会在本地被拒绝，无法继续完成商品输入。本次把「本次选择的照片」与「最终用于识别的照片组」分开处理。

## 2. 用户交互

| 编号 | 操作 | 实际行为 |
| --- | --- | --- |
| 01 | 拍一张照片 | 仅请求相机，数量为 1，成功后追加到当前照片组 |
| 02 | 从相册补充 | 仅请求相册，最多选择剩余空位，不替换现有照片 |
| 03 | 重拍 | 仅替换点选的那一张，保留其他照片与顺序 |
| 04 | 移除 | 只删除当前本地选择；移除后可继续拍摄或补图 |
| 05 | 取消选择 | 保留已有照片及当前上传批次，不显示制作失败 |
| 06 | 拒绝授权 | 给出可重试提示，已有照片保留；不回显底层错误内容 |
| 07 | 开始识别商品 | 满足 3–5 张及全部本地条件后才能提交，无需填写商品表单 |

页面显示「整体拍全、侧面换角度、细节看清楚」、已添加数量及还差几张。五张满额时禁止继续添加，仍可重拍或移除。开始按钮在少于三张和正在处理照片时禁用，避免重复操作。

## 3. 输入及资源约束

JPG/PNG、单张不超过 10MB、总量不超过 50MB、短边至少 640px、像素不超过 30MP；按实际原始文件字节计算 SHA，重复照片在选入时拒绝。相册追加/替换必须再次检查完整集合；不截取前五张、不静默丢弃已选照片。

提交函数在登录、创建草稿及上传之前检查完整集合，因此其他调用方不能绕过页面按钮提交一张照片。真实图片解码、类型、摘要、自动旋转及元数据剥离继续由原服务端执行，本次不改变服务端规格。

本地照片字节和临时路径仅存于页面内存，不写入恢复存储。页面销毁后需要重新选择本地照片，不能把已失效临时路径显示为上传成功。已上传素材仍由原服务端状态和订单记录恢复。

## 4. 原批次与账户恢复

照片数量、顺序或内容变化时，页面建立新批次；取消和未改变的选择保留原批次。恢复记录只保存照片组摘要及业务 ID，不保存照片内容。

相同批次只允许同一照片组摘要。已建草稿的批次被换图、重排或历史记录缺少摘要时，提交前返回 `PHOTO_BATCH_CHANGED`，不把新照片绑定回原草稿，也不覆盖原上传。

相同照片组重试继续使用原草稿、上传授权、完成回执和绑定的幂等键。新照片组开始后清除旧识别、方案、预览、报价和订单的本地快捷引用，保留已存在的服务端订单与账户素材库。用户仍可从「我的素材」找到原订单。

异步创建草稿、完成绑定和识别返回后都重验当前账户；旧账户结果不能写入新账户的恢复记录。

## 6. 截图与复录

实际运行共享页面的补充截图、MP4/WebM/GIF和 SHA 清单位于 `docs/media/photo-capture/`。其中照片是自绘商品的合成浏览器返回，用于验证逐张累计、单张重拍、满额和移除，不宣称支付宝/抖音真机相机授权或真实识别已验收。

先执行 `delivery:build`，然后在项目根目录运行：

```powershell
.\scripts\run.ps1 exec tsx scripts/record-photo-capture.ts
```

脚本只启动本项目的本地预览服务，使用临时无头浏览器，并在成功/失败退出时关闭本次上下文、浏览器与本次服务。原有全流程演示保留为历史页面录像；最新拍照交互以此补充录制为准。

English: the shared Alipay/Douyin photo page accepts one camera photo at a time, appends album picks up to five, and supports targeted retake/removal. Only a valid 3–5-photo group can start analysis. Cancellation preserves the set; retries preserve original upload identities. Changing a sold/uploading batch cannot overwrite its original group, and switching to a new group clears stale local navigation references. Native device permissions and real recognition still require separate acceptance.
