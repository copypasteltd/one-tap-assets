# 商品档案轻量纠错与同版续制 v1.0

本增补落实 P01-F03/F06/F12 的售前档案纠错。支付宝、抖音小程序继续以“拍照→自动识别→选择方案”为正常路径；识别页面仅增加可选的“识别有误？补充一处纠错”。用户不必填写商品表单或逐项确认字段。

## 1. 用户操作与版本

用户主动展开纠错，选择名称、类别、可见特征、标签文字或照片用途，只填写这一处。名称最多200字、类别120字，其余文字1000字；可见特征、标签文字和照片用途必须选择当前商品的依据照片，名称/类别可选关联。不新增照片、付费调用或订单。

保存后生成新档案和新商品身份锁，增加草稿版本，原档案和原锁保持不可变。后续推荐按新档案刷新；原未付款计划、预览和报价引用清除，继续所选方案时重新使用当前档案编排。已付款订单、价格、期限和权益保留原合同，不自动重新制作。

用户补充的特征/标签文字保留 `USER_CORRECTED`、照片及纠错来源，并在页面标为“你的纠错（待复核）”。它们不进入仅由 OBSERVED/OCR 形成的商品锁事实，不消除未知项；后续仍须证据和独立复核。现有模型观察、识别摘要和未知信息保留其来源，不因用户输入升级成模型观察事实。

## 2. 提交、未知回执与并发

复用 `POST /v1/p01/products/{product_id}/corrections`，不改变契约或增加操作。请求绑定本人商品、原档案ID、预期草稿版本、单一字段及依据照片；幂等键由原请求确定。

回执丢失时保留当前内存中的原请求，表单冻结，用户点击“核对原提交”沿用同一键和正文。后端回放原结果后，客户端读取当前商品指针和档案，核对照片、档案、商品锁、摘要及版本后才更新界面。读取到并发的新版本时提示重新读取，不覆盖该版本。

两个不同请求争用同一预期版本时，原草稿行锁与事务只接受一个，另一请求返回版本冲突。另一账户或商品的依据照片不得引用；重复依据、纯空白、超长字段和超过档案容量均在写入前拒绝。原接口允许1000字纠错，但 Profile 名称/类别上限更短；本轮补上这两个字段限制，并在任何新档案写入前校验完整 Profile，避免持久化不符合响应契约的版本。

## 3. 页面、账户与私有输入

纠错表单及原提交只放在页面内存，不进入恢复存储、URL、Cookie或日志。离页/卸载中止本页等待并清理表单，不能将取消等待解释为服务端未执行；重进重新读取当前档案。用户也可明确放弃当前表单并重新读取。

请求发送和每次返回后重新核对账户及当前商品；换号、切草稿、离页后的迟到响应不填回当前页面。识别读取辅助函数也补上这些范围检查，旧账户的数据在重新加载时隐藏。实际产品不传递个人令牌到录制入口。

视觉复用方案C奶白/深绿、橙色主动作、薄荷次动作与原共享组件，17个小程序页面保持。新纠错属于识别页内可选区域，不另设购买关卡。

## 4. 使用与验证

按[启动文档](../delivery/README.md)准备原生依赖，构建并启动 API/Worker。使用双小程序的商品档案页查看本人的有效档案，展开可选纠错；纠错本身不需要重新运行多模态、不收取制作费用。首次真实识别仍需要正式视觉服务与授权配置。

专项覆盖原键回放、两请求并发、跨账户/照片拒绝、字段/容量边界、原档案不变、用户标签不提升为事实、新版照片用途、旧计划引用清理及迟到响应。浏览器录制使用实际共享 React/Taro 页面与明确的合成产品/网络回执；原生数据库接口检查独立验证真实事务。两者不能替代真实多模态质量、小程序真机或正式支付验收。

复录先构建当前源码，使用项目内浏览器缓存、TEMP/TMP，执行 `pnpm docs:profile`。脚本关闭自己创建的页面、浏览器和静态预览服务，不关闭用户其他标签、服务或原生开发数据库。

本轮不运行全面测试，不要求全面绿灯。真实服务与生产隔离、完整官方/社区商业准入、真机、完整F17、Plus/云端与58项完整验收仍待完成。此前旧官方订单用例240秒超时尚未解决；本轮在原快照再次观察到 PLAN_ROLE 阶段原生测试进程以 `0xc0000374` 崩溃，原因未确认，独立保存记录，不能将纠错专项通过称为该订单已通过。
